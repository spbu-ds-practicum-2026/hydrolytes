# Передача для API-разработчиков: маршрутизация по шардам

> Документ для `services/api-gateway` (и любого сервиса, который ходит в БД по `user_id`).
> От: DB-части проекта. Источник истины по схеме БД — `services/database/`.

---

## 2. Контракт хеш-кольца (менять нельзя по одиночке!)

```python
from hashring import HashRing
ring = HashRing(["shard1", "shard2"])   # имена шардов — стабильные, НЕ адреса
shard = ring.get(user_id)               # -> 'shard1' | 'shard2'
```

Три константы-контракта, **одинаковые у всех сервисов**:

```
алгоритм = md5 | vnodes = 64 | состав = ["shard1", "shard2"]
```

Если любой сервис возьмёт другой алгоритм/состав — маршруты разойдутся и данные
пользователя «разъедутся» по шардам. Меняется состав шардов — меняется **все сразу**.

Почему в кольцо идут **имена**, а не `host:port`: при failover меняется адрес,
но не имя шарда → маршрутюзера не меняется, переезжают только «двери».

## 3. Откуда брать адрес шарда (координатор)

Адреса — **динамика**. Два файла на стенде:

- `services/database/deploy/stand.json` — статика: шард → порты;
- `C:/pgstand/stand_state.json` — состояние: у каждого шарда `epoch`.

**Правило чётности:** чётный `epoch` → мастер = `master_port`; нечётный → мастер = `replica_port`.

```python
import json

cfg  = json.load(open(r"D:\vs\spbu\Dispersed_calcs\hydrolytes\services\database\deploy\stand.json"))
st   = json.load(open(r"C:\pgstand\stand_state.json"))

def current_master(shard: dict) -> tuple[str, int]:
    """(host, port) действующего мастера шарда с учётом failover."""
    epoch = st[shard["name"]]["epoch"]
    port = shard["master_port"] if epoch % 2 == 0 else shard["replica_port"]
    return "127.0.0.1", port          # в распределённой схеме — IP устройства шарда
```

Запись — **только на этот порт**. Порт реплики (`replica_port` при чётном epoch и т.д.)
read-only: `INSERT` туда получит `ERROR: cannot execute … in a read-only transaction`.

> Сейчас (одна машина) — читаем файлы. По ТР позже координатор должен отдавать
> карту маршрутов по HTTP с `epoch`; API сверяет epoch и не применяет устаревшую карту.

## 4. Подключение к шарду

```python
import psycopg
host, port = current_master(shard)
conn = psycopg.connect(host=host, port=port, user="postgres", dbname="postgres")
```

- локальный стенд: аутентификация trust на localhost, паролей нет;
- распределённая схема (4 устройства): на каждом узле БД —
  `listen_addresses = '*'` в `postgresql.conf` и `host all all <сеть>/24 scram-sha-256`
  в `pg_hba.conf` (**никогда не `trust` наружу**), брандмауэр — только локальная сеть.

## 5. Поведение при failover (обязательно к реализации)

1. **Кольцо НЕ перестраивается** — `ring.get(user_id)` до и после promote даёт одинаковый шард.
2. Меняется только адрес у координатора (`epoch` растёт на 1) → переподключиться и продолжить.
3. Пока шард мигрирует/недоступен — отдавать коды из `docs/api.md`:
   `MIGRATING` (идёт переключение), `UNAVAILABLE` (узел недоступен), `NOT_FOUND`.
4. На повторе после `UNAVAILABLE` — заново спросить карту маршрутов (адрес мог смениться).
5. `ring` и карта координатора опрашиваются с разной периодичностью:
   кольцо — один раз при старте сервиса (оно статичное), карта — регулярно.
