# Координатор стенда

Знает, где сейчас мастер каждого шарда, и сам повышает реплику, если мастер пропал.

Владелец: инфраструктура.

## Что делает (v0)

| Функция | Как |
|---|---|
| Проверка узлов | `pg_isready` по порту мастера и реплики, раз в секунду |
| Failover | после `failures_before_promote` неудач подряд — `pg_ctl promote` реплики |
| Отсечение старого мастера | `epoch` увеличивается при каждом promote; маршруты с меньшим `epoch` недействительны |
| Деградированный режим | реплика пропала, мастер жив → `synchronous_commit = local`, возврат при возврате реплики |
| Карта маршрутов | печатает состояние; в проекте отдаётся сервисам Mail |

## Чего пока нет

- HTTP-эндпоинта с картой маршрутов (сейчас только консоль и файл состояния);
- второго шарда в конфиге;
- возврата старого узла в роли реплики (сейчас делает `pg_basebackup` руками);
- оркестрации переноса диапазона и статуса `migrating`.

## Запуск

```powershell
python --version            # нужен 3.9+
python coordinator.py --config ..\database\deploy\stand.json
```

Ожидаемый вывод в спокойном состоянии:

```
[shard1] master=up replica=up epoch=0 state=healthy
```

## Проверка failover

В отдельном окне остановите мастер:

```powershell
& "C:\Program Files\PostgreSQL\16\bin\pg_ctl.exe" -D C:\pgstand\shard1 -m immediate stop
```

Координатор через три проверки напечатает promote, поднимет `epoch` до 1 и переключит маршрут на порт реплики. Состояние сохраняется в файл `state_file` из конфига — сервисы читают его как источник маршрутов.

## Тесты

```powershell
python -m pytest
```

Тесты не поднимают настоящие кластеры: проверяются решения «кого повышать» и «когда включать деградацию» на подставных проверках.
