# Техническое решение проекта «Почтовый сервер»

## Введение

- **Краткое описание:**  
  «Почтовый сервер» — учебный проект, реализующий прототип распределённой почтовой системы. Система позволяет отправлять и получать письма по протоколу SMTP, читать почту и управлять письмами через веб-интерфейс. Проект демонстрирует ключевые принципы построения отказоустойчивых и масштабируемых распределённых приложений.

- **Цель проекта:**  
  реализовать прототип распределённой почтовой системы, которая доставляет письма пользователям и сохраняет их в соответствующих папках.

- **Задачи:**  
  закрепить теоретические основы распределённых систем (масштабируемость, отказоустойчивость, консистентность) через практическую реализацию; продемонстрировать применение концепций курса: ненадёжная доставка сообщений, частичные отказы, распределение данных и нагрузки, модели согласованности и интеграцию сервисов в распределённый конвейер обработки данных.

## Глоссарий
| Термин        | Определение |
|---------------|-------------|
| Почтовый ящик | Учётная запись пользователя, хранящая входящие и исходящие письма. |
| Письмо        | Сообщение с заголовками (From, To, Subject, Message-ID) и телом; единица хранения и доставки. |
| Message-ID    | Уникальный идентификатор письма, назначаемый при отправке; используется для дедупликации доставки одного письма, но не определяет, являются ли два запроса одной операцией отправки. Для входящего SMTP повтор без Message-ID определяется по ограниченному составному отпечатку сообщения и получателя. |
| SMTP          | Протокол передачи почты между серверами (RFC 5321) и от клиента к серверу. |
| MX-запись     | DNS-запись, указывающая, какой сервер принимает почту для домена. |
| Папка         | Системное хранилище писем в ящике: «Входящие» (письма, адресованные пользователю) и «Отправленные» (копии отправленных им писем). Письмо попадает в папку по смыслу операции — при приёме или при отправке; пользовательских папок, ручного перемещения писем между папками и «Корзины» в объёме проекта нет. |
| API Gateway   | Точка входа для всех клиентских запросов веб-интерфейса. |
| Шард          | Независимый сегмент данных, размещённый на отдельном узле или группе узлов; в учебном стенде шардирование выполняется по `userId`. |
| Хеш-кольцо    | Способ распределения ключей по узлам (consistent hashing): узлы и ключи отображаются хеш-функцией на кольцо, ключ принадлежит ближайшему узлу по часовой стрелке. |
| Виртуальный узел | Дополнительная точка хеш-кольца, принадлежащая физическому узлу; повышает равномерность распределения ключей. |
| Узел хранения | Совокупность экземпляров PostgreSQL, размещённых на одном физическом устройстве. В стенде два узла хранения: узел A (устройство 2) и узел B (устройство 3). **Отказ узла хранения** — отказ всех экземпляров PostgreSQL на этом устройстве; прикладные сервисы, запущенные на том же устройстве, при этом продолжают работать. |
| Отказ устройства целиком | Отказ всех процессов на физическом устройстве, включая прикладные сервисы. На устройстве 3 работают только экземпляры PostgreSQL, поэтому для него «отказ устройства целиком» совпадает с «отказом узла хранения». На устройствах 1, 2 и 4 вместе с БД работают прикладные сервисы, поэтому отказ этих устройств целиком — отдельный, более широкий сценарий, который в объём гарантий не входит (кроме отказа одного инстанса Mail). |
| Мастер        | Узел PostgreSQL, принимающий записи в пределах своего шарда; остальные узлы шарда — реплики, доступные только для чтения. |
| Реплика       | Узел PostgreSQL в режиме восстановления (`pg_is_in_recovery() = true`), непрерывно применяющий WAL мастера своего шарда и готовый быть повышенным до мастера. |
| Потоковая репликация | Штатный механизм PostgreSQL: резервный узел получает базовую копию (`pg_basebackup`) и непрерывно применяет поток WAL мастера (`primary_conninfo`, `restore_command`). |
| Синхронная репликация | Режим записи, при котором COMMIT на мастере подтверждается только после применения записи на резервном узле того же шарда (`synchronous_standby_names`, `synchronous_commit = remote_apply`). Подтверждённая запись существует минимум на двух узлах. |
| Failover      | Автоматическое переключение на резервный узел при отказе основного: координатор стенда повышает реплику до мастера (`pg_ctl promote`) и публикует новую карту маршрутизации с новым `epoch`. |
| Временная линия WAL (timeline) | Номер ветви журнала WAL, который создаётся при промоушене реплики. Ветвь старого мастера после промоушена считается устаревшей, поэтому его разошедшиеся записи не могут стать частью системы. |
| Fencing       | Изоляция отказавшего мастера, исключающая его дальнейшие записи (защита от split-brain). Не опирается на осведомлённость старого мастера о новом состоянии; обеспечивается двумя внешними барьерами: (1) отзыв маршрута у координатора — новые записи на старый узел не направляются и не подтверждаются клиенту; (2) новая временная линия WAL у промоутированной реплики — при возврате старый мастер принимается только как реплика и пересоздаётся из копии нового мастера, а сделанные им в изоляции записи отбрасываются. |
| Деградированный режим шарда | Состояние шарда после failover, пока у него остался единственный живой узел: записи продолжают приниматься, но без синхронной репликации (`synchronous_commit = local`) до возврата второго узла шарда. |
| Инстанс Mail  | Отдельный экземпляр сервиса Mail, не хранящий состояния: два инстанса за API Gateway обслуживают клиентские запросы, при отказе одного запросы переносятся на другой. |
| Журнал обработанных событий (inbox) | Таблица в Analytics DB с уникальным `eventId`, фиксирующая факт обработки события; вставка отметки и запись результата выполняются одной транзакцией, поэтому повторная доставка не меняет результат. |
| Идемпотентность | Свойство операции: повтор того же запроса с тем же ключом операции (например, после потери ответа) не создаёт новый эффект. Одинаковые получатель, тема и текст сами по себе не означают одну операцию: две намеренные отправки остаются двумя письмами. |
| Ключ операции | Идентификатор конкретного запроса пользователя, позволяющий распознать его повтор после потери ответа; для новой намеренной отправки создаётся новый ключ. |
| Задание доставки | Надёжно сохранённая запись о необходимости передать письмо на шард получателя. Хранит `status` (`pending`, `in_progress`, `done`, `failed`), владельца `locked_by`, срок аренды `lease_until` и число попыток `attempts`; обрабатывается с повторами и помечается выполненной только после успешной записи и только текущим владельцем. |
| Аренда задания (lease) | Ограниченный по времени захват задания инстансом Mail: владелец продлевает аренду heartbeat-ом, а при его отказе аренда истекает и задание забирает другой инстанс. Владение — сохранённое состояние строки, а не блокировка транзакции. |
| Окно переноса диапазона (`migrating`) | Состояние диапазона ключей при перераспределении данных: изменяющие операции по этому диапазону отклоняются с кодом `MIGRATING` и повторяются после переключения маршрута, чтение продолжается. Нужно для согласованного переноса без разрешения конфликтов версий. |
| At-least-once | Семантика доставки сообщений: сообщение доставляется как минимум один раз, возможны дубли. |
| Transactional outbox | Паттерн: событие записывается в outbox-таблицу в той же транзакции, что и изменение данных, затем пересылается в брокер с повторами. |
| Message Broker | Посредник для асинхронной передачи событий между сервисами; может доставить одно событие более одного раза. |
| Analytics   | Сервис учёта событий доставки: принимает события `message.accepted` и `message.delivered` из брокера, дедуплицирует их по `eventId` и ведёт историю доставки (какое письмо, когда и на каком этапе доставлено). Содержимое писем не анализируется, ML-классификации в системе нет. |
| Event-ID    | Уникальный идентификатор факта изменения или действия; отличается от идентификатора письма и ключа операции. |
| Дедупликация  | Отбрасывание повторно доставленных копий одного события по идентификатору события; разные события для одного письма не отбрасываются. |
| Координатор стенда | Компонент учебного стенда, который выполняет health-проверки узлов, при отказе мастера повышает реплику (`pg_ctl promote`), увеличивает поколение шарда (`epoch`) и распространяет актуальную карту маршрутизации с номером временной линии WAL. Отказ самого координатора вне объёма проекта. |
| Health-проверка | Периодический или выполняемый после таймаута запрос, проверяющий доступность и готовность узла принимать операции. |
| Поколение шарда (`epoch`) | Монотонно увеличиваемый номер текущего владельца шарда, который хранит координатор и публикует вместе с адресом мастера и номером временной линии WAL. Mail отправляет записи только тому узлу, чей `epoch` совпадает с текущим в карте координатора; при несовпадении операция отклоняется с требованием обновить маршрут. Само число не является механизмом изоляции: изолированный узел о новом `epoch` не узнаёт и продолжает считать себя мастером, поэтому изоляцию обеспечивают отзыв маршрута и отбрасывание разошедшегося WAL (см. Fencing). |
| Eventual consistency | Модель согласованности: при отсутствии новых обновлений все копии данных со временем сходятся к одному состоянию. |

## Функциональные требования
Система должна предоставлять следующие функции:
1. Отправка писем пользователям внутри системы и на внешние почтовые домены по SMTP.  
2. Приём входящих писем по SMTP от внешних серверов и от внутренних пользователей.  
3. Просмотр почты через веб-интерфейс: список папок «Входящие» и «Отправленные» с количеством писем, открытие письма с отображением заголовков и тела; открытие письма помечает его прочитанным.
4. Удаление письма: выбранное правило — безвозвратное удаление. Команда удаления убирает письмо из папки, после чего письмо недоступно пользователю; «Корзина» и восстановление удалённых писем в объём проекта не входят. Повторное удаление уже удалённого письма не является ошибкой и возвращает прежний результат операции.
5. Просмотр истории доставки: пользователь видит по каждому отправленному письму два статуса конвейера — «принято в доставку» (исходная копия и задание доставки сохранены Mail DB) и «доставлено получателю» (письмо записано на шард получателя) — с временем каждого события. Отдельный признак «событие зафиксировано в истории доставки» показывает, что запись о доставке учтена сервисом Analytics; он относится только к учёту события в журнале и не означает никакой обработки содержимого письма. Классификация, категоризация и другие ML-функции в системе отсутствуют.

### Ограничения на предметную область

1. Почта работает только в пределах одного домена (например, `mail.example`); внешняя доставка демонстрируется через локальную SMTP-заглушку, а настоящие внешние домены и аутентификация SPF/DKIM/DMARC находятся вне объёма проекта.
2. Поддерживаются только текстовые письма.
3. Пользовательские ящики создаются администратором, самообслуживающая регистрация вне объёма проекта.

## Нефункциональные требования



1. **Сохранность результата отправки:** повтор того же запроса отправки с тем же ключом операции (например, после потери ответа) не создаёт вторую копию в папках пользователя. Намеренная новая отправка с теми же получателем, темой и текстом создаёт отдельное письмо с новым `Message-ID`. Уже подтверждённое системой письмо и его метаданные не теряются при отказе узла хранения; после восстановления пользователь видит тот же результат отправки и может повторить запрос без создания дубликата.
2. **Отказоустойчивость:** система должна продолжать работать в двух независимо проверяемых сценариях отказа: (а) **отказ одного узла хранения** — всех экземпляров PostgreSQL на устройстве 2 или 3, при этом прикладные сервисы на этих устройствах остаются живы; (б) **отказ одного инстанса Mail**. В сценарии (а) недоступность обнаруживается по таймаутам и health-проверкам: при отказе мастера шарда координатор повышает доступную реплику (failover) и публикует новую карту маршрутизации, а при отказе реплики при живом мастере шард переходит в деградированный режим и записи не блокируются. В сценарии (б) запросы продолжает обслуживать второй инстанс за API Gateway, а задания отказавшего инстанса перехватываются по истечении аренды. За границами гарантии и названы явно: отказ двух узлов хранения одновременно, отказ устройства 1 целиком (API Gateway, Web Client и `Mail-1`), отказ устройства 2 целиком (узлы БД вместе с `Mail-2` и SMTP Gateway) и отказ устройства 4 (координатор, брокер, Analytics). Для устройства 3 отказ устройства целиком входит в гарантию, так как на нём работают только экземпляры PostgreSQL (см. глоссарий и раздел «План разработки»).
3. **Доставка событий:** семантика at-least-once; повторная доставка того же события не приводит к его повторной обработке (идемпотентность потребителя), но разные события для одного письма обрабатываются независимо. Отметка об обработке события и результат обработки фиксируются одной транзакцией, а подтверждение брокеру отправляется только после успешного commit. Поэтому повторная доставка не может ни потерять событие (ack до commit), ни применить его дважды (сначала история, потом отметка).
4. **Понятность интерфейса:** результат каждой операции пользователя однозначно отображается в веб-интерфейсе: письмо отправлено, получено, прочитано, удалено или операция отклонена с объяснением причины.
5. **Работа при отказе узла хранения:** при отказе всех экземпляров PostgreSQL одного устройства пользователь продолжает работать: мастер шарда переключается на реплику другого узла, а доступ к данным второго шарда сохраняется на его мастере. Прикладные сервисы, работающие на том же устройстве, при этом не затрагиваются. Операции, требующие данных шарда, у которого недоступны оба узла хранения, отклоняются с понятным сообщением о временной недоступности, а не завершаются молчаливой ошибкой. После восстановления доступа уже подтверждённые письма и папки доступны в прежнем состоянии; подтверждённые письма не удаляются и не создаются повторно.
6. **Консистентность:** одно письмо не доставляется дважды при повторных SMTP-сессиях и повторной доставке одного события (дедупликация по `Message-ID` письма и идентификатору события соответственно); при отсутствии новых операций состояние папок и история доставки сходятся к полному состоянию (eventual consistency).  
7. **Восстановление данных после сбоев доставки событий:** после прекращения новых операций и восстановления доставки событий Analytics учитывает все сохранённые события, включая накопившиеся во время сбоя, ровно один раз по каждому идентификатору события.
8. **Сохранность записи при failover:** подтверждённая клиенту запись существует минимум на двух узлах, поэтому отказ одного узла хранения не приводит к её потере. В деградированном режиме шарда (после failover, пока второй узел не вернулся) запись подтверждается по одному узлу: это явное ограничение, о котором система сообщает в интерфейсе и логах, а синхронная репликация возвращается после восстановления второго узла шарда.

## Пользовательские сценарии



### Сценарий: отправка письма

**Участник:** авторизованный пользователь.

1. Пользователь открывает форму создания письма.
2. Пользователь указывает получателя, тему и текст письма и нажимает «Отправить».
3. Система сообщает об успешной отправке и показывает письмо в папке «Отправленные».
4. Получатель видит письмо в папке «Входящие».
5. Если ответ на отправку потерян, пользователь повторяет тот же запрос с тем же ключом операции: система не создаёт дубликат и показывает ранее полученный результат. Две намеренные отправки с одинаковыми получателем, темой и текстом являются отдельными письмами.

### Сценарий: получение письма

**Участник:** локальная SMTP-заглушка, имитирующая внешний отправитель, и получатель почты.

1. Локальная SMTP-заглушка открывает SMTP-сессию и имитирует внешний отправитель, отправляя письмо на адрес пользователя.
2. SMTP Gateway принимает письмо от заглушки и передаёт его в Mail.
3. Mail проверяет `Message-ID` в области конкретного ящика и помещает письмо во «Входящие». Если `Message-ID` отсутствует, Mail использует составной отпечаток заголовков и тела вместе с адресом получателя только для защиты от повтора этому получателю; такое письмо не считается глобально дедуплицированным для других получателей.
4. После успешного сохранения письма SMTP Gateway отвечает заглушке `250 OK`. Этот ответ означает, что письмо принято системой, но не является доказательством настоящей доставки во внешний домен.
5. Получатель открывает интерфейс и читает содержимое письма.

### Сценарий: чтение письма

**Участник:** получатель почты.

1. Пользователь открывает папку «Входящие» и видит список писем с отправителем, темой, датой и признаком прочтения.
2. Пользователь открывает письмо.
3. Система показывает заголовки (From, To, Subject, Message-ID) и тело письма и отмечает письмо прочитанным.
4. После возврата в список письмо отображается как прочитанное.

### Сценарий: удаление письма

**Участник:** получатель почты.

1. Пользователь удаляет письмо из папки; интерфейс предупреждает, что удаление безвозвратное.
2. Система удаляет письмо и сообщает результат операции.
3. Письмо исчезает из папки и больше не отображается в интерфейсе, при открытии по прямой ссылке возвращается «письмо не найдено».
4. Повторная команда удаления того же письма не является ошибкой: система возвращает прежний результат операции и не создаёт новую запись.

### Сценарий: просмотр истории доставки

**Участник:** отправитель письма.

1. Пользователь открывает страницу истории доставки.
2. Система показывает список отправленных писем со статусами «принято в доставку» и «доставлено получателю», временем каждого события и дополнительным признаком «зафиксировано в истории доставки» — отметкой о том, что событие учтено сервисом Analytics. Содержимое писем нигде не анализируется и не классифицируется.
3. Если брокер недоступен, история по последним письмам временно неполна, и интерфейс сообщает, что данные обновляются; после восстановления доставки событий статусы дополняются без дублей.

## Архитектура системы

Система построена как набор сервисов, взаимодействующих синхронно через API Gateway и асинхронно через Message Broker. Синхронный контур отвечает за приём пользовательских запросов и SMTP-сообщений, а асинхронный контур — за учёт событий доставки и ведение истории доставки. Содержимое писем нигде не анализируется и не классифицируется.

Основные компоненты:

1. **Web Client** — веб-интерфейс пользователя для работы с папками и письмами.
2. **SMTP Gateway** — принимает входящие SMTP-сессии от внешних серверов и внутренних клиентов, выполняет базовый разбор письма и передаёт его в Mail.
3. **API Gateway** — единая точка входа для запросов веб-клиента; выполняет маршрутизацию в Mail и Analytics, а также возвращает клиенту однозначный результат операции.
4. **Mail** — основной сервис почтовой системы. Он обрабатывает отправку и приём писем, проверяет ключ операции и `Message-ID`, выбирает шард по `userId`, управляет папками и записывает задания доставки и события в transactional outbox. Сервис не хранит состояния и запускается в двух взаимозаменяемых инстансах (`Mail-1`, `Mail-2`) за API Gateway.
5. **Message Broker** — передаёт события из transactional outbox в Analytics с семантикой at-least-once.
6. **Analytics** — потребляет события `message.accepted` и `message.delivered`, дедуплицирует их по `eventId` и ведёт историю доставки. Отметка об обработке и результат фиксируются одной транзакцией, подтверждение брокеру отправляется после commit.
7. **Analytics DB** — хранит историю обработанных событий и агрегированные сведения о доставке.
8. **Mail DB** — транзакционное шардированное хранилище писем, папок, ключей операций, заданий межшардовой доставки и outbox-событий на PostgreSQL 16. Шард — отдельный кластер со своим мастером и одной синхронной репликой; репликация потоковая, штатными средствами PostgreSQL. Мастер и реплика одного шарда всегда находятся на разных физических узлах хранения.
9. **Координатор стенда** — единственный владелец решения о смене владельца шарда и о состоянии кольца. Он выполняет health-проверки узлов (`pg_isready`, `pg_is_in_recovery`, отставание реплики, `pg_stat_replication`), при отказе мастера повышает реплику (`pg_ctl promote`), при отказе реплики переводит шард в деградированный режим и возвращает синхронный режим после её возврата, увеличивает поколение шарда (`epoch`) и публикует карту маршрутизации: логический шард → адрес мастера и реплики, `epoch`, номер временной линии WAL, признак деградации, признак переноса диапазона (`migrating`). Он же оркестрирует перераспределение при изменении кольца: замораживает диапазон, запускает перенос, сверяет контрольные суммы и переключает маршрут. Координатор не пытается «заблокировать» недоступный узел: изоляция достигается отзывом маршрута и новой временной линией WAL.
10. **Локальная SMTP-заглушка внешней доставки** — имитирует успешную передачу письма во внешний домен; настоящая внешняя SMTP-доставка не входит в учебный scope.

### Шардирование и репликация Mail DB

- **Проблема:** объём писем и нагрузка на операции с почтой растут, а отказ одного узла не должен приводить к потере подтверждённых писем.
- **Выбор хранилища:** Mail DB — PostgreSQL 16, по кластеру на логический шард. Выбраны штатные механизмы вместо собственной реализации: потоковая репликация WAL, `synchronous_commit = remote_apply` для подтверждения записи на двух узлах, транзакции с уникальными ограничениями (ключ операции, `Message-ID` в пределах ящика, `eventId`) и встроенное понятие временной линии WAL, которое даёт готовый признак актуальной ветви истории записей. Собственный консенсус-протокол не пишется: координатор — небольшой сервис на Python, который вызывает `pg_ctl` и раздаёт карту маршрутов. PostgreSQL используется как инфраструктура хранения и как поставщик одного примитива — промоушена реплики; партиционирование, перераспределение данных, детекция отказа, порядок переключения, fencing и политика деградации проектируются командой (см. следующий пункт). Автономные менеджеры отказоустойчивости (Patroni, `pg_auto_failover`, managed-сервисы с автоматическим переключением) намеренно не используются: иначе решение по failover действительно было бы делегировано готовому продукту.
- **Схема стенда (единая во всех разделах):** два физических узла хранения, два логических шарда, по одной реплике на шард.

  | Логический шард | Мастер | Синхронная реплика |
  |-----------------|--------|--------------------|
  | Шард 1 | узел БД A (устройство 2) | узел БД B (устройство 3) |
  | Шард 2 | узел БД B (устройство 3) | узел БД A (устройство 2) |

  На каждом узле хранения работают два экземпляра PostgreSQL на разных портах: мастер одного шарда и реплика другого. Поэтому мастер и реплика одного шарда всегда находятся на разных физических узлах. Сервисы при этом не делят судьбу узла хранения: API Gateway и `Mail-1` — на устройстве 1, `Mail-2` и SMTP Gateway — на устройстве 2, координатор, брокер и Analytics — на устройстве 4 (см. «План разработки»). Устройство 3 занято только экземплярами PostgreSQL, поэтому его отказ — чистый отказ узла хранения.
- **Кольцо и маршрутизация:** consistent hashing по `userId`, по 64 виртуальных узла на логический шард; ключ принадлежит ближайшему виртуальному узлу по часовой стрелке. Координатор публикует карту: логический шард → адрес мастера, адрес реплики, `epoch`, номер временной линии WAL, признак деградации. Mail держит локальную копию карты и обновляет её по health-запросу (TTL 1 с) и по событию смены `epoch`.
- **Как принимается запись:** Mail по кольцу определяет шард для `userId`, берёт из карты адрес мастера и `epoch` и выполняет транзакцию. Шард настроен синхронно: `synchronous_standby_names = 'replica_shardN'`, `synchronous_commit = remote_apply`. COMMIT не возвращается, пока запись не применена на реплике, поэтому подтверждённая запись существует на двух узлах. Чтение по умолчанию идёт на мастера (read-your-writes); реплика используется как кандидат на промоушен и для отчётных чтений.
- **Детекция отказа:** Mail фиксирует ошибку соединения или таймаут 2 с; координатор на каждой health-проверке (интервал 1 с) выполняет `pg_isready` и `SELECT pg_is_in_recovery()`, и после трёх неудач подряд объявляет мастер недоступным. Отказ реплики координатор обнаруживает по `pg_stat_replication`: строка синхронной резервной копии пропала или её `sync_state` перестал быть `sync` дольше трёх интервалов проверки.
- **Отказ реплики при живом мастере (обратный случай):** если резервный узел шарда недоступен, а мастер работает, синхронный режим начинает блокировать COMMIT — мастер ждёт подтверждения от узла, которого больше нет, и записи по шарду зависают. Поэтому координатор сразу переводит этот шард в деградированный режим: `synchronous_commit = local` и пустой `synchronous_standby_names`, после чего записи продолжают подтверждаться одним узлом. Признак деградации публикуется в карте. Когда реплика возвращается, координатор проверяет её временную линию, пересоздаёт как реплику мастера, ждёт догон WAL и только затем возвращает `remote_apply` и синхронный режим (критерий — `sync_state = sync`). Записи при этом не блокируются ни на одном этапе.
- **Failover:** координатор — единственный владелец решения о смене владельца шарда. Он проверяет кандидата (реплика доступна, применяет WAL, отставание в допустимых пределах), выполняет `pg_ctl promote` на реплике, увеличивает `epoch` и публикует новую карту. Mail перестаёт отправлять записи на старый адрес, получает карту и повторяет операцию на новом мастере (retry), если предыдущая попытка не была подтверждена клиенту. Задержка ограничена таймаутом детекции и промоушеном (несколько секунд).
- **Fencing — два внешних барьера и явная модель отказов:**
  1. *Отзыв маршрута.* Единственный источник адреса мастера — карта координатора. После смены `epoch` записи на старый узел не направляются, и клиенту они не подтверждаются.
  2. *Новая временная линия WAL.* Промоушен создаёт новую ветвь журнала; старый мастер остаётся на старой. При возврате он не может снова стать мастером, потому что разошёлся с актуальной линией: он пересоздаётся из `pg_basebackup` нового мастера (или подтягивается через `pg_rewind` как реплика), и все записи, сделанные им в изоляции, отбрасываются. Поэтому механизм изоляции не требует, чтобы старый мастер «узнал» новый `epoch`: его записи просто никогда не попадают в актуальную ветвь истории.
  3. *Модель отказов стенда — crash-stop.* Узел либо работает, либо останавливается: в демонстрации координатор останавливает процесс PostgreSQL (`pg_ctl stop -m immediate`) на устройстве с отказавшим узлом, и этот процесс не продолжает работу. Возврат узла выполняется контролируемо, только как реплики нового мастера.
  4. *Сетевая изоляция (живой, но отрезанный от сети мастер) в объём не входит* и заявлена как ограничение: для неё нужен распределённый fencing. Запланированное расширение: мастер продлевает lease (TTL 5 с) у координатора и при недоступности координатора дольше TTL сам переводит себя в режим только для чтения (`default_transaction_read_only = on`), а каждая запись дополнительно сверяет `epoch` с координатором. Тогда разделение сети не позволяет двум мастерам одновременно подтверждать записи. В текущий DoD этот пункт не входит.
- **Новые записи после продвижения единственной резервной реплики:** после промоушена у шарда остаётся один живой узел, синхронного standby нет, и подтверждение записи «на двух узлах» невозможно. Координатор переводит новый мастер в деградированный режим: `ALTER SYSTEM SET synchronous_commit = local` и пустой `synchronous_standby_names`, затем `pg_reload_conf()`. Записи продолжают приниматься и подтверждаться, но гарантия временно ослаблена до одного узла; признак деградации публикуется в карте, показывается в интерфейсе и пишется в лог. Записи не блокируются в ожидании реплики — это осознанный выбор доступности вместо долговечности (AP-поведение), и он назван явно как компромисс.
- **Возврат узла и восстановление синхронности:** вернувшийся узел стартует с `default_transaction_read_only = on` и без маршрута; координатор проверяет его временную линию, пересоздаёт его как реплику актуального мастера (`pg_basebackup`), ждёт догон WAL и только затем возвращает `synchronous_commit = remote_apply` и `synchronous_standby_names`. Критерий готовности — `pg_stat_replication`: `sync_state = sync` и `replay_lsn` догнал `flush_lsn`.
- **Что именно отказывает на демонстрации:** в первом сценарии отказывает узел хранения B — все экземпляры PostgreSQL на устройстве 3. На этом устройстве запущены только два экземпляра — мастер шарда 2 и реплика шарда 1, других сервисов там нет, поэтому «отказ узла хранения» и «отказ устройства 3 целиком» здесь совпадают. Отказ моделируется остановкой обоих экземпляров БД (`pg_ctl stop -m immediate`). Тем самым демонстрация проверяет отказ именно узла хранения, а не отдельного процесса, и ровно в этих границах сформулированы НФТ 2 и НФТ 5. Второй сценарий — отказ инстанса `Mail-1`: останавливается только процесс `Mail-1`, а БД, координатор, SMTP Gateway и `Mail-2` продолжают работать. Демонстрация показывает: (1) детекцию отказа и failover шарда 2 на его реплику на узле A; (2) деградированный режим шарда 2; (3) продолжение работы шарда 1 на своём мастере, у которого пропала реплика; (4) контролируемый возврат узла B как реплики. Для шарда 1 это одновременно и проверка обратного случая: его мастер жив, а синхронная реплика пропала, поэтому координатор переводит шард 1 в деградированный режим и записи продолжают подтверждаться одним узлом, не зависая. Честно названное следствие: пока реплика шарда 1 отсутствует, повторный отказ мастера шарда 1 привёл бы к недоступности записи по этому шарду — система сообщит об этом понятной ошибкой, а не потеряет данные. API Gateway, оба инстанса Mail, SMTP Gateway, координатор, брокер и Analytics при этом живы, потому что размещены на других устройствах. Что в объёме демонстрации не проверяется и прямо названо ограничением: отказ устройства 1 (API Gateway вместе с `Mail-1`) и отказ устройства 4 (координатор, брокер, Analytics); отказ инстанса Mail демонстрируется отдельно — остановкой процесса `Mail-1`, а не всего устройства. Одновременный отказ двух узлов хранения также вне объёма.
- **Перераспределение данных при изменении кольца:** добавление нового логического шарда (например, шарда 3 при масштабировании) меняет только диапазоны ключей, попадающие к новым виртуальным узлам; остальные ключи остаются на месте — в этом и состоит свойство consistent hashing. Перенос идёт по диапазонам владения `user_id` и выполняется **согласованно, через короткое окно запрета изменений**: перенос без остановки записи (двойная запись, разрешение конфликтов версиями) для учебного проекта не требуется и сознательно не реализуется.
  1. *Планирование.* Координатор по новому кольцу вычисляет диапазоны `user_id`, которые переходят к шарду 3. Диапазон переносится целиком; ключи вне диапазона не затрагиваются.
  2. *Замирание диапазона (freeze).* Координатор публикует карту с признаком `migrating` для диапазона и увеличивает `epoch`. Mail, получив карту, отклоняет **изменяющие** операции по `userId` из этого диапазона с кодом `MIGRATING`: интерфейс сообщает «раздел обновляется, повторите через несколько секунд» и повторяет запрос сам. Цель — не более 30 с на диапазон.
     Это и закрывает вопрос про «воскрешение» удалённого письма и потерю отметки о прочтении: пока диапазон заморожен, удаление и пометка о прочтении не могут произойти между чтением источника и записью в цель. Переносчик снимает копию с источника, в котором ничего не меняется, поэтому переносится ровно то состояние, что было на момент замирания, и ни одно изменение не теряется — изменений просто нет. Чтение из двух шардов для этого не нужно и не используется.
  3. *Копирование.* Переносчик копирует данные диапазона пачками: письма (включая `is_read`), папки, ключи операций, задания доставки и outbox-события. Копирование выполняется через `INSERT ... ON CONFLICT DO NOTHING`, поэтому повторный запуск переносчика после сбоя безопасен.
  4. *Сверка до переключения.* Координатор сверяет по каждому `user_id` количество писем и контрольную сумму (например, `md5(string_agg(message_id, ',' ORDER BY message_id))`), количество ключей операций и заданий доставки. При расхождении перенос отменяется, диапазон остаётся за старым шардом, а данные не теряются — источник не удалялся.
  5. *Переключение маршрута.* После успешной сверки координатор публикует новую карту и новый `epoch`: диапазон закреплён за шардом 3, признак `migrating` снят. Mail начинает писать и читать только в новом владельце; отклонённые в окне `MIGRATING` операции повторяются и находят своё место уже на шарде 3.
  6. *Связанные данные.* Ключи идемпотентности переносятся вместе с диапазоном, поэтому повтор принятой операции после смены владельца по-прежнему находит свой результат: поиск идёт по `(user_id, operation_key)`, а `user_id` маршрутизируется уже в шард 3. Задания доставки и outbox-события диапазона тоже переносятся: outbox-релей и обработчик заданий работают по локальной таблице своего шарда, поэтому после переключения продолжают публиковать и доставлять их на шарде 3 — задания и события не теряются. К началу копирования по диапазону не должно оставаться активных аренд: координатор дожидается, пока задания диапазона не перейдут в `pending` или `done`, поэтому переносится только спокойное состояние.
  7. *Удаление источника.* Строки диапазона на шарде-источнике удаляются только после переключения маршрута и истечения окна отката (10 минут), чтобы ошибку сверки можно было исправить без потери данных.
  - **Демонстрация:** добавление третьего шарда к двум; показ, что переместилась только часть пользователей; изменение и удаление во время окна `MIGRATING` отклоняются с понятным кодом и успешно повторяются после переключения; сверка количества и контрольных сумм совпала; письмо и отметка о прочтении после переноса те же; повтор ранее принятой операции возвращает сохранённый результат, а не создаёт новую.
  - **Компромиссы:** изменения по части пользователей на время переноса отклоняются (до 30 с на диапазон); удаление источника отложено на окно отката; перенос без остановки записи и разрешение конфликтов версиями не реализуются.
- **Гарантия учебного стенда:** кольцо из двух логических шардов маршрутизирует ящики по `userId`; подтверждённая запись зафиксирована на двух узлах; при отказе мастера система автоматически повышает реплику, продолжает обслуживать записи и после возврата узла восстанавливает синхронную репликацию; при отказе реплики записи не блокируются; при добавлении шарда переносится только доля ключей, а изменяющие операции по переносимому диапазону на время переноса отклоняются и повторяются.
- **Компромиссы:** синхронная репликация увеличивает задержку подтверждения записи и требует явной обработки отказа резервного узла (иначе COMMIT зависает); в деградированном режиме гарантия долговечности ослаблена до одного узла; операции, затрагивающие ящики разных пользователей, требуют координации между шардами; перераспределение ключей требует короткого окна запрета изменений для переносимого диапазона.

### Доставка событий и идемпотентность

- **Проблема:** брокер или соединение с ним может временно отказать, а повторная доставка события может создать дубликат аналитических данных.
- **Решение:** событие записывается в outbox в одной транзакции с изменением Mail DB и отправляется в Message Broker с повторами до подтверждения. `eventId` детерминирован: `accepted:<message_id>` и `delivered:<message_id>:<recipient_user_id>`, поэтому повторное формирование события идемпотентно. Outbox-релей работает на каждом инстансе Mail и забирает строки через `FOR UPDATE SKIP LOCKED` с флагом `published`, поэтому два инстанса не мешают друг другу, а возможная повторная публикация гасится дедупликацией в Analytics. Mail различает ключ операции, `Message-ID` письма и `eventId`: повтор запроса с тем же ключом операции не создаёт второе письмо, повтор одного SMTP-события не создаёт вторую доставку, а Analytics дедуплицирует повторно доставленные события по `eventId`.
- **Атомарная фиксация обработки:** у Analytics есть таблица истории доставки с уникальным `eventId` и журнал обработанных событий (inbox) с тем же ключом. Обработка одного события — одна транзакция: `INSERT INTO processed_event(event_id, received_at, result) VALUES (...) ON CONFLICT (event_id) DO NOTHING RETURNING event_id` и, только если строка вставилась, изменение агрегатов истории в той же транзакции. Затем `COMMIT`. Подтверждение брокеру (`basic_ack`) отправляется после commit, при выключенном авто-подтверждении. Если потребитель упал до commit — транзакция откатывается и событие будет доставлено снова; если упал после commit, но до ack — событие придёт повторно, конфликт по `event_id` отбросит вставку, и результат не изменится. Так исключены оба опасных порядка: «сначала отметка, потом результат» (потеря) и «сначала результат, потом отметка» (двойной учёт). Раннее подтверждение брокеру (до commit) не используется.
- **Гарантия:** применяется at-least-once без потери сохранённых событий; повторная обработка одного события не создаёт дубль в истории доставки, а эффект обработки ровно один (exactly-once effect). После восстановления доставки Analytics сходится к полному состоянию.
- **Компромиссы:** история доставки может временно отставать от состояния Mail DB, зато отказ брокера не приводит к потере событий.

### Обработка частичных отказов

- SMTP Gateway подтверждает приём письма только после того, как Mail сохранил его результат в Mail DB.
- При временной недоступности Message Broker outbox сохраняет события до успешной повторной отправки.
- При отказе узла Mail DB операции, требующие недоступных данных, отклоняются с понятным сообщением, а уже подтверждённые данные восстанавливаются после failover.
- Таймауты, health-проверки, retry и fencing используются совместно: retry применяется для временных ошибок, failover — для подтверждённого отказа мастера, а fencing предотвращает записи старого узла и split-brain за счёт отзыва маршрута и новой временной линии WAL.
- При отказе одного инстанса Mail API Gateway переносит запросы на второй инстанс; состояние хранится только в Mail DB, поэтому переключение не требует синхронизации инстансов.
- При отказе узла хранения шард переходит в деградированный режим и обслуживает записи на единственном узле; это состояние видно в интерфейсе и логах, а не маскируется.

### Отказоустойчивость инстансов Mail: передача владения работой

- **Проблема:** отказ инстанса Mail не должен прерывать обслуживание пользователей и, что важнее, не должен оставлять «зависшую» работу. В отличие от узла хранения, здесь нечего повышать: у инстанса нет реплики, но у него есть работа, которую он в этот момент выполнял — забранные задания доставки, недописанные записи, незавершённые SMTP-сессии.
- **Почему это не повторяет failover БД.** В failover БД свойство — «подтверждённая запись не теряется, шард продолжает принимать записи»; состояние там реплицируется, реплика повышается, клиент повторяет запрос. Здесь состояние не реплицируется и повышать нечего: проблема обратная — у погибшего инстанса остались *в работе* задания, и они не должны ни зависнуть навсегда, ни выполниться дважды. Обнаружение отказа и retry в обоих случаях есть, но они одинаковы по природе и как отдельное свойство не заявляются: заявляется **передача владения незавершённой работой (ownership handover)**, которой в failover БД нет.
- **Механика владения.** Задание доставки в Mail DB содержит `status` (`pending`, `in_progress`, `done`, `failed`), `locked_by`, `lease_until`, `attempts`. Владение — это сохранённое состояние строки, а не блокировка транзакции. Захват пачки одним запросом атомарно ставит статус, владельца и срок аренды:

  ```sql
  UPDATE delivery_job
  SET status      = 'in_progress',
      locked_by   = :self,
      lease_until = now() + interval '10 seconds',
      attempts    = attempts + 1
  WHERE id IN (
    SELECT id FROM delivery_job
    WHERE status = 'pending'
       OR (status = 'in_progress' AND lease_until < now())
    ORDER BY created_at
    LIMIT 50
    FOR UPDATE SKIP LOCKED
  )
  RETURNING *;
  ```

- **Почему одной блокировки недостаточно.** `FOR UPDATE SKIP LOCKED` разводит два инстанса только на время этой транзакции. После `COMMIT` задание недоступно другому инстансу благодаря сохранённому состоянию: в строке уже стоят `status = 'in_progress'` и будущий `lease_until`, поэтому ни первая ветка `WHERE` (`status = 'pending'`), ни вторая (`lease_until < now()`) его не выбирают. Именно поэтому перевод в `in_progress` выполняется в том же `UPDATE`, что и назначение владельца и срока аренды: если бы статус оставался `pending`, задание подходило бы под первую ветку и второй инстанс забрал бы его немедленно.
- **Heartbeat и потеря владения.** Пока идёт работа, каждые 3 с выполняется `UPDATE delivery_job SET lease_until = now() + interval '10 seconds' WHERE id = ANY(:ids) AND locked_by = :self;`. Если обновлено меньше строк, чем ожидалось, владение потеряно (lease истёк и задание перехватил другой инстанс) — инстанс прекращает работу над этими заданиями и не фиксирует результат.
- **Завершение и защита от двойного выполнения.** Завершение задания всегда включает проверку владения: `UPDATE ... SET status = 'done', locked_by = NULL, lease_until = NULL WHERE id = :id AND locked_by = :self`. Ноль обновлённых строк означает, что задание уже перехвачено другим инстансом, и результат не фиксируется. Как именно группируются записи в транзакции — зависит от шардов, см. следующий пункт. После 5 неудачных попыток (`attempts`) задание переводится в `failed` и отображается администратору, чтобы не перебиралось бесконечно.
- **Завершение межшардового задания: две локальные транзакции, а не одна.** Задание доставки хранится на шарде отправителя, а письмо и событие — на шарде получателя; при разных шардах это разные кластеры PostgreSQL, поэтому одной транзакцией их не зафиксировать. Порядок совпадает с основным техническим сценарием:
  1. на шарде получателя — локальная транзакция: запись письма во «Входящие» и событие `message.delivered` в outbox получателя; `COMMIT` подтверждается синхронной репликой;
  2. на шарде отправителя — отдельная локальная транзакция: `UPDATE delivery_job SET status = 'done', locked_by = NULL, lease_until = NULL WHERE id = :id AND locked_by = :self`.

  Во время переноса диапазона получателя (признак `migrating`) шард получателя отвечает на запись письма ошибкой `MIGRATING`. Она трактуется как **временная, а не как неудачная попытка**: задание возвращается в `pending`, `attempts` не увеличивается, `locked_by` и `lease_until` сбрасываются, и обработчик берёт его снова после окончания переноса. Поэтому письмо не теряется и не уходит в `failed` из-за переноса, а лимит попыток расходуется только на настоящие ошибки.
  Отказ между двумя фиксациями — штатная ситуация, а не ошибка: задание остаётся `in_progress` с истекающим lease, и через ≤10 с его забирает живой инстанс. Повтор безопасен, потому что обе операции идемпотентны: письмо вставляется по уникальному `Message-ID` в пределах ящика (`ON CONFLICT DO NOTHING`), событие — по детерминированному `eventId` вида `delivered:<message_id>:<recipient_user_id>` (тоже `ON CONFLICT DO NOTHING`). Второе выполнение не создаёт ни второго письма, ни второго события, а `status = 'done'` выставляется один раз. Если оба ящика попали на один шард, письмо, событие и `status = 'done'` фиксируются одной локальной транзакцией — этот случай описан в техническом сценарии отправки. Протокол распределённых транзакций (2PC) не используется.
- **Что даёт lease и почему без него не работает.** Если инстанс умирает, его задания просто перестают продлеваться: через 10 с `lease_until` истекает, и их забирает живой инстанс (`FOR UPDATE SKIP LOCKED` не даёт двум инстансам взять одно задание). Без lease задание, взятое мёртвым инстансом, осталось бы в статусе «в работе» навсегда — доставка зависла бы без всякой ошибки в логах. Без идемпотентности по `Message-ID` повторный захват задания привёл бы к двойной доставке. Поэтому свойство звучит так: **ни одно задание не остаётся без владельца и ни одно не выполняется дважды**.
- **Какие действия остаются доступны при отказе `Mail-1`:**

  | Действие | Состояние | Как обеспечивается |
  |---|---|---|
  | Отправка письма | доступно | запрос уходит в `Mail-2` через API Gateway |
  | Чтение, удаление, список папок | доступно | данные в Mail DB, `Mail-2` их обслуживает |
  | История доставки | доступно | запрос к Analytics через API Gateway |
  | Приём входящего по SMTP | доступно | SMTP Gateway направляет письмо в `Mail-2` |
  | Фоновая доставка уже принятых писем | доступно с задержкой до 10 с | задания с истёкшим lease забирает `Mail-2` |
  | Единичный запрос, попавший в момент отказа | повторяется один раз | таймаут 2 с, повтор в `Mail-2` с тем же ключом операции |

- **Границы.** Отказ обоих инстансов Mail означает недоступность клиентского контура — гарантия дана для отказа одного инстанса. Отказ API Gateway и отказ узла с координатором в объём не входят (см. НФТ 2). Отказ узла хранения Mail DB рассматривается отдельно, в разделе «Шардирование и репликация».
- **Демонстрация гарантии:**
  1. `Mail-1` запускает обработку пачки из 20 заданий доставки и показывает их как `in_progress` с владельцем `Mail-1`;
  2. в этот момент процесс `Mail-1` останавливается — половина заданий остаётся в работе;
  3. в интерфейсе отправка, чтение и удаление продолжают работать: запросы обслуживает `Mail-2`;
  4. через ≤10 с lease истекает, `Mail-2` забирает осиротевшие задания (`locked_by = Mail-2`), и все письма доставляются;
  5. итог: 20 писем, 20 записей во «Входящих», ни одного задания в статусе `in_progress`, дублей нет — проверяется запросом по `delivery_job` и по папке получателя.
- **Компромиссы:** задержка доставки при отказе ограничена lease-интервалом (выбран 10 с как компромисс между скоростью восстановления и ложными захватами при кратковременных подвисаниях); lease требует heartbeat, то есть одного фонового цикла на инстанс; при кратковременном сетевом подвисании возможен ложный захват, поэтому идемпотентность записи по `Message-ID` обязательна; обнаружение отказа и повтор запроса на `Mail-2` — вспомогательный механизм, он не заявляется как отдельное свойство, поскольку совпадает по природе с уже описанным в failover БД.


### Модели согласованности

- Mail DB является источником истины для писем и папок; операции изменения выполняются транзакционно.
- Для одного письма дедупликация доставки выполняется по `Message-ID`, для событий — по `eventId`, а пользовательские запросы отправки повторяются идемпотентно по ключу операции.
- Агрегаты истории доставки обновляются в той же транзакции, что и отметка об обработке события, поэтому расхождений между историей и журналом обработки не возникает.
- Analytics DB обновляется асинхронно и допускает eventual consistency: после прекращения новых операций и восстановления доставки событий история доставки сходится к состоянию всех сохранённых событий без дублей.
- Реплика шарда отстаёт от мастера, но не более чем на момент последнего применённого WAL; чтение по умолчанию выполняется на мастере, поэтому пользователь всегда видит свои подтверждённые изменения (read-your-writes). В деградированном режиме шарда система остаётся доступной, но подтверждение записи даётся одним узлом.

## Технические сценарии

### Сценарий: отправка письма внутри системы

1. Клиент отправляет в API Gateway запрос POST /messages с параметрами: recipient, subject, body и отдельный идемпотентный ключ операции. `Message-ID` создаётся Mail для нового письма.
2. API Gateway перенаправляет запрос в сервис Mail.
3. Инстанс Mail по локальной копии хеш-кольца определяет шарды отправителя и получателя (хеш от userId).
4. В локальной транзакции на шарде отправителя письмо записывается в папку «Отправленных», сохраняется ключ операции с результатом запроса, создаётся надёжное задание доставки получателю и в outbox пишется событие `message.accepted`. Транзакция завершается синхронно: COMMIT подтверждается после применения записи на реплике шарда (`synchronous_commit = remote_apply`), поэтому подтверждённая копия существует на двух узлах.
5. Mail сообщает API Gateway о принятии письма в доставку. Это подтверждение означает, что исходная копия и задание доставки сохранены; завершение доставки получателю отслеживается отдельно.
6. Фоновый обработчик заданий берёт задание по аренде (`status = 'in_progress'`, `locked_by`, `lease_until`) и идемпотентно записывает письмо на шард получателя по `Message-ID` — вместе с событием `message.delivered` в outbox, одной транзакцией; после ошибки повторяет попытки, а задание помечает выполненным отдельной транзакцией на шарде отправителя и только при совпадении `locked_by` (см. «Отказоустойчивость инстансов Mail»). Если отправитель и получатель попадают на один и тот же шард, запись в «Отправленные», запись во «Входящие», событие `message.delivered` и отметка о выполнении задания выполняются одной транзакцией.
7. Outbox-релей публикует события `message.accepted` и `message.delivered` в Message Broker (at-least-once, publisher confirm), а Analytics дедуплицирует их по `eventId`.
8. Повтор запроса с тем же ключом операции возвращает сохранённый результат первой операции и не создаёт новое письмо. Новая намеренная отправка получает новый ключ операции и новый `Message-ID`.

```mermaid
sequenceDiagram
  participant Client
  participant APIGateway
  participant Mail
  participant ShardA
  participant ShardB
  participant Outbox as Outbox шардов A и B
  participant MessageBroker
  participant Analytics
  participant AnalyticsDB

  Client->>APIGateway: POST /messages — recipient, subject, body, операция с ключом
  APIGateway->>Mail: Запрос отправки
  Mail->>Mail: Определить шарды отправителя и получателя по хеш-кольцу
  Mail->>ShardA: Письмо в «Отправленных» + ключ операции + задание доставки + событие message.accepted в outbox — одна транзакция
  ShardA-->>Mail: OK, commit подтверждён на реплике
  Mail-->>APIGateway: Принято в доставку
  APIGateway-->>Client: Запрос принят
  Mail->>ShardB: Записать во «Входящие» по Message-ID + событие message.delivered в outbox — одна транзакция
  ShardB-->>Mail: OK, commit подтверждён на реплике
  Mail->>ShardA: Пометить задание доставки выполненным
  Outbox->>MessageBroker: Публикация message.accepted и message.delivered с eventId, at-least-once
  MessageBroker->>Analytics: Доставка события, возможен дубль
  Analytics->>AnalyticsDB: Отметка обработки + история — одна транзакция, затем ack
  Client->>APIGateway: Повтор запроса с тем же ключом операции
  APIGateway->>Mail: Запрос отправки
  Mail->>ShardA: Найти сохранённый результат по ключу операции
  ShardA-->>Mail: Результат первой операции
  Mail-->>Client: Запрос принят (без второй операции)
```

### Сценарий: просмотр истории доставки

1. Пользователь открывает страницу истории в веб-интерфейсе.
2. API Gateway запрашивает у Analytics сведения о доставке писем.
3. Analytics возвращает историю доставки, уже дедуплицированную при обработке событий: по каждому письму собираются события `message.accepted` («принято в доставку») и `message.delivered` («доставлено получателю») с временем каждого.
4. Пользователь видит актуальную историю; при задержке брокера последние события ещё не учтены, интерфейс сообщает, что данные обновляются, а после восстановления доставки статусы дополняются без дублей.

```mermaid
sequenceDiagram
  participant Client
  participant APIGateway
  participant Analytics
  participant AnalyticsDB

  Client->>APIGateway: GET /delivery-history
  APIGateway->>Analytics: Запрос истории доставки
  Analytics->>AnalyticsDB: Прочитать историю доставки
  AnalyticsDB-->>Analytics: Записи по письмам — дубли отброшены ещё при обработке eventId
  Analytics-->>APIGateway: История доставки со статусами и временем
  APIGateway-->>Client: 200 OK (история)
```

### Сценарий: отказ мастера шарда

1. Во время обработки запросов мастер шарда 2 на узле БД B перестаёт отвечать. В демонстрации используется модель crash-stop: координатор останавливает процесс PostgreSQL (`pg_ctl stop -m immediate`), и узел не продолжает работу.
2. Инстанс Mail получает ошибку соединения или таймаут 2 с и не подтверждает операцию клиенту.
3. Координатор на health-проверке (`pg_isready`, `SELECT pg_is_in_recovery()`, интервал 1 с) фиксирует недоступность; после трёх неудач подряд мастер объявляется отказавшим.
4. Координатор проверяет кандидата — реплику шарда 2 на узле БД A: она доступна, применяет WAL, отставание в допустимых пределах.
5. Координатор выполняет `pg_ctl promote` на реплике: она становится мастером и создаёт новую временную линию WAL. Старый мастер остаётся на предыдущей линии и носителем актуальной истории записей больше не является.
6. Координатор переводит новый мастер в деградированный режим (`synchronous_commit = local`, `synchronous_standby_names = ''`), так как второй узел шарда недоступен, увеличивает `epoch` шарда 2 и публикует новую карту маршрутизации (адрес мастера, `epoch`, номер временной линии, признак деградации).
7. Mail обновляет карту и повторяет неподтверждённую операцию на новом мастере. Ранее подтверждённые записи читаются с нового мастера без изменений: они были применены на реплике до отказа.
8. Клиент получает успешный ответ; интерфейс показывает, что шард работает в деградированном режиме.
9. Позже узел B возвращается контролируемо: стартует с `default_transaction_read_only = on`, пересоздаётся как реплика нового мастера через `pg_basebackup`, догоняет WAL. После проверки `pg_stat_replication` (`sync_state = sync`) координатор возвращает `synchronous_commit = remote_apply` и синхронную репликацию.
10. Записи, сделанные старым мастером в изоляции, при пересоздании отбрасываются и в систему не попадают.

```mermaid
sequenceDiagram
  participant Client
  participant APIGateway
  participant Mail
  participant Coordinator
  participant OldMaster as Мастер шарда 2 — узел БД B
  participant NewMaster as Реплика шарда 2 — узел БД A

  Client->>APIGateway: Запрос операции
  APIGateway->>Mail: Операция
  Mail->>OldMaster: Запрос к мастеру шарда 2
  OldMaster--xMail: Таймаут — ответа нет
  Coordinator->>OldMaster: pg_isready и pg_is_in_recovery — 3 неудачи
  OldMaster--xCoordinator: Узел недоступен
  Coordinator->>NewMaster: Проверить доступность и отставание WAL
  NewMaster-->>Coordinator: Реплика доступна, WAL применяется
  Coordinator->>NewMaster: pg_ctl promote — новая временная линия WAL
  NewMaster-->>Coordinator: Новый мастер готов
  Coordinator->>NewMaster: synchronous_commit = local (деградированный режим)
  Coordinator->>Coordinator: epoch шарда 2 += 1
  Coordinator-->>Mail: Новая карта: мастер, epoch, timeline, признак деградации
  Mail->>NewMaster: Повтор неподтверждённой операции (retry)
  NewMaster-->>Mail: OK
  Mail-->>APIGateway: Успех
  APIGateway-->>Client: Операция выполнена (шард деградирован)
  Note over Coordinator,NewMaster: Возврат узла B — только как реплики: read-only, pg_basebackup, догон WAL, затем remote_apply
```

### Сценарий: отказ инстанса Mail

1. `Mail-1` обрабатывает пачку заданий доставки: они помечены `in_progress` с `locked_by = Mail-1` и продлеваемым lease.
2. Инстанс `Mail-1` перестаёт отвечать (процесс остановлен), при этом Mail DB, координатор и второй инстанс доступны. Часть его заданий остаётся в статусе `in_progress`.
3. API Gateway получает ошибку соединения или таймаут 2 с, health-проверка `/health` три раза подряд неуспешна, и `Mail-1` исключается из балансировки.
4. Запрос пользователя переотправляется в `Mail-2` с тем же ключом операции; если операция уже была подтверждена ранее, возвращается сохранённый результат, поэтому дубль не создаётся.
5. SMTP Gateway направляет входящие письма на доступный инстанс.
6. Через ≤10 с lease осиротевших заданий истекает; `Mail-2` забирает их `SELECT ... FOR UPDATE SKIP LOCKED`, доставляет письма и помечает задания выполненными — осиротевших заданий не остаётся, двойной доставки нет.
7. Клиент получает результат операции; после восстановления `Mail-1` снова включается в балансировку и начинает продлевать lease только по своим новым заданиям.

```mermaid
sequenceDiagram
  participant Client
  participant APIGateway
  participant Mail1 as Mail-1
  participant Mail2 as Mail-2
  participant MailDB as Mail DB

  Client->>APIGateway: Запрос операции
  APIGateway->>Mail1: Запрос (активный инстанс)
  Mail1--xAPIGateway: Нет ответа / таймаут 2 с
  APIGateway->>Mail1: health /health (3 неудачи подряд)
  Mail1--xAPIGateway: Недоступен — исключён из балансировки
  APIGateway->>Mail2: Тот же запрос с тем же ключом операции
  Mail2->>MailDB: Выполнить операцию (или вернуть сохранённый результат)
  MailDB-->>Mail2: Результат
  Mail2-->>APIGateway: Успех
  APIGateway-->>Client: Операция выполнена
  Note over Mail1,MailDB: Задания Mail-1 остались в статусе in_progress с истёкшим lease
  Mail2->>MailDB: Забрать задания с истёкшим lease (FOR UPDATE SKIP LOCKED)
  MailDB-->>Mail2: Осиротевшие задания переданы Mail-2
  Note over Mail1,MailDB: Ни одно задание не зависло и не выполнено дважды
```

### Сценарий: потеря и повторная доставка события

1. При записи письма получателю в той же транзакции создаётся событие `message.delivered` с уникальным `eventId` в outbox-таблице шарда. Либо письмо и событие сохранены вместе, либо не сохранено ничего.
2. Outbox-релей выбирает неопубликованные строки и отправляет их в брокер с publisher confirm; строка помечается опубликованной только после подтверждения.
3. Message Broker временно недоступен — подтверждения нет, релей повторяет отправку (at-least-once).
4. В результате брокер может доставить одно и то же событие в Analytics более одного раза.
5. Analytics обрабатывает событие одной транзакцией: вставка отметки в журнал обработанных событий (`INSERT INTO processed_event(event_id, result) ... ON CONFLICT (event_id) DO NOTHING RETURNING event_id`) и, только если строка вставилась, обновление истории доставки — всё в той же транзакции.
6. После `COMMIT` отправляется подтверждение брокеру. Если ack потерян и событие придёт снова, конфликт по `event_id` не даст ни повторно учесть событие, ни изменить историю.
7. Раннее подтверждение (ack до commit) не используется, поэтому падение потребителя между обработкой и commit приводит к повторной доставке, а не к потере события.
8. История доставки сходится к полному состоянию без дублей — eventual consistency.

```mermaid
sequenceDiagram
  participant Mail
  participant Outbox
  participant MessageBroker
  participant Analytics
  participant AnalyticsDB

  Mail->>Outbox: message.delivered (eventId) — в одной транзакции с записью письма на шарде получателя
  Mail->>Mail: отдельная транзакция на шарде отправителя — status = done при совпадении locked_by
  Outbox->>MessageBroker: Публикация события
  MessageBroker--xOutbox: Недоступен, publisher confirm не получен
  Outbox->>MessageBroker: Повтор публикации (retry)
  MessageBroker-->>Outbox: Подтверждение — строка помечена опубликованной
  MessageBroker->>Analytics: Доставка события (возможен дубль)
  Analytics->>AnalyticsDB: BEGIN — вставка processed_event(event_id) ON CONFLICT DO NOTHING
  alt первая доставка — вставка прошла
    Analytics->>AnalyticsDB: Обновление истории доставки (та же транзакция)
    AnalyticsDB-->>Analytics: COMMIT
    Analytics-->>MessageBroker: ack после commit
  else повтор — конфликт по event_id
    AnalyticsDB-->>Analytics: 0 строк, история не меняется
    Analytics-->>MessageBroker: ack после commit, повтор не учтён
  end
  Note over Analytics: Эффект ровно один, история без дублей — eventual consistency
```

## План разработки и тестирования

План рассчитан на команду до четырёх человек. Все сервисы должны запускаться локально или на доступных учебных устройствах; для демонстрации не требуются отдельные облачные кластеры и настоящие внешние почтовые домены. Внешний SMTP и брокер сообщений допускается заменить локальными тестовыми заглушками или контейнерами.

**Включает:**

- реализацию API Gateway и минимального веб-интерфейса;
- реализацию сервиса Mail для отправки, приёма, чтения и безвозвратного удаления текстовых писем;
- реализацию SMTP Gateway для демонстрации приёма письма;
- хранение писем, папок и ключей идемпотентности в транзакционной базе данных;
- интеграцию Message Broker или его локальной учебной реализации для событий;
- реализацию transactional outbox и дедупликации событий в Analytics;
- простую историю доставки писем и агрегированные сведения о доставленных сообщениях;
- атомарную обработку событий в Analytics: журнал обработанных событий, фиксация результата одной транзакцией и подтверждение брокеру после commit;
- реализацию локального учебного стенда на PostgreSQL: фиксированное кольцо из двух логических шардов, по одной синхронной реплике на шард, координатор, `epoch` и автоматический failover;
- перераспределение диапазонов при добавлении третьего шарда с окном запрета изменений и сверкой контрольных сумм;
- два инстанса Mail за API Gateway: аренда заданий с heartbeat и захватом осиротевших заданий, перенос запросов при отказе одного инстанса.

Локальные SMTP-клиент, внешняя SMTP-доставка и Message Broker допускается реализовать как учебные компоненты или контейнеры. Заглушка внешней доставки используется только для демонстрации интерфейса отправки и не считается настоящей доставкой во внешний домен. Для outbox, дедупликации, сохранения подтверждённых писем и failover используются работающие локальные компоненты стенда, а не заглушки, возвращающие заранее заданный успех.

**План разработки:**

1. Уточнить форматы данных и API для писем, папок и истории доставки. Зафиксировать сценарии демонстрации.
2. Реализовать транзакционную модель Mail DB на PostgreSQL: пользователи, текстовые письма, папки, `Message-ID`, ключи операций, задания доставки и outbox.
3. Реализовать сервис Mail: отправка и приём текстовых писем, проверка повторного запроса, чтение и безвозвратное удаление писем.
4. Реализовать API Gateway и минимальные страницы веб-интерфейса для списка папок, просмотра, отправки и удаления писем.
5. Реализовать SMTP Gateway и локальный сценарий приёма входящего письма без подключения к настоящей DNS/MX-инфраструктуре.
6. Добавить Message Broker или локальную очередь, публикацию событий из outbox и повторную отправку неподтверждённых событий.
7. Реализовать Analytics: журнал обработанных событий, атомарную фиксацию результата и истории в одной транзакции, подтверждение брокеру после commit, историю доставки и её отображение в интерфейсе.
8. Реализовать учебный стенд Mail DB на PostgreSQL: фиксированное кольцо из двух логических шардов, по одной синхронной реплике каждого шарда на другом физическом узле, consistent hashing по `userId`, координатор, `epoch`, карта маршрутизации и fencing через отзыв маршрута и новую временную линию WAL.
9. Реализовать автоматический failover шардов (`pg_ctl promote`), деградированный режим после промоушена, возврат узла как реплики и восстановление синхронного режима.
10. Реализовать перераспределение ключей при добавлении третьего логического шарда: окно `migrating` с отклонением изменяющих операций, перенос диапазонов владения (письма, ключи операций, задания доставки, outbox), сверка контрольных сумм и согласованное переключение маршрута.
11. Реализовать два инстанса Mail за API Gateway: аренда заданий с heartbeat и захватом осиротевших заданий, health-проверки, исключение отказавшего инстанса из балансировки и повтор запроса во второй инстанс.
12. Добавить проверку задержки брокера и повторной доставки событий на работающем локальном брокере или учебной реализации очереди, включая падение потребителя до commit и потерю ack.
13. Подготовить README с командами запуска, тестовыми пользователями, примерами запросов, размещением сервисов на устройствах и последовательностью демонстрации; отдельно указать, что внешняя SMTP-доставка является заглушкой.

Работу можно распределить по четырём устройствам (участникам) следующим образом:

1. **Устройство 1:** Web Client, API Gateway, инстанс `Mail-1`.
2. **Устройство 2:** инстанс `Mail-2`, SMTP Gateway, узел БД A (мастер шарда 1 и реплика шарда 2).
3. **Устройство 3:** узел БД B (мастер шарда 2 и реплика шарда 1).
4. **Устройство 4:** координатор стенда, Message Broker, Analytics и Analytics DB.

При такой схеме мастер и реплика каждого шарда находятся на разных узлах хранения (устройства 2 и 3), а координатор, брокер и Analytics размещены на устройстве 4. Так как на одном устройстве параллельно работают несколько сервисов, различаем две единицы отказа: **отказ узла хранения** (все экземпляры PostgreSQL на устройстве) и **отказ устройства целиком** (все процессы на нём).

| Сценарий отказа | Что перестаёт работать | Что остаётся доступно | В гарантии |
|---|---|---|---|
| Узел хранения B = устройство 3 целиком | мастер шарда 2 и реплика шарда 1 | failover шарда 2 на реплику на устройстве 2; шард 1 работает в деградированном режиме; веб-интерфейс, отправка, приём по SMTP | **да**, демонстрируется |
| Узел хранения A — только экземпляры PostgreSQL на устройстве 2 | мастер шарда 1 и реплика шарда 2 | failover шарда 1 на реплику на устройстве 3; шард 2 в деградированном режиме; `Mail-2` и SMTP Gateway живы, запросы и приём почты продолжаются | **да**, покрывается теми же механизмами |
| Инстанс `Mail-1` (процесс) | обработка заданий и обслуживание запросов этим инстансом | `Mail-2` обслуживает запросы, осиротевшие задания перехватываются по истечении аренды, SMTP Gateway направляет почту в `Mail-2` | **да**, демонстрируется отдельно |
| Устройство 2 целиком (БД + `Mail-2` + SMTP Gateway) | узлы БД, `Mail-2`, SMTP Gateway | failover шарда 1; запросы обслуживает `Mail-1`; **приём входящих по SMTP недоступен** | **нет**, названо ограничением |
| Устройство 1 целиком (`Mail-1` + API Gateway + Web Client) | клиентский доступ полностью | серверная часть: приём по SMTP и фоновая доставка | **нет** |
| Устройство 4 целиком (координатор, брокер, Analytics) | координатор, публикация событий, история доставки | почта работает, outbox копит события, failover недоступен до возврата координатора | **нет** |

Гарантия «система продолжает работать» дана для отказа одного узла хранения и для отказа одного инстанса Mail. Отказ устройств 1, 2 и 4 целиком в объём гарантий не входит и назван явно, чтобы обещания не расходились с демонстрацией.

Координатор считается доступным постоянно; отказ самого координатора и восстановление его состояния не входят в учебный scope.

**План тестирования:**

- модульные тесты Mail для создания письма, чтения и безвозвратного удаления;
- модульные тесты идемпотентности: повтор запроса с тем же ключом операции не создаёт второе письмо, а новая отправка с новым ключом создаёт отдельное письмо;
- тест дедупликации по `Message-ID` при повторном приёме одного SMTP-сообщения;
- тесты API Gateway для корректных и некорректных запросов, несуществующего письма и недоступной операции;
- интеграционный тест записи письма и события outbox в одной транзакции;
- тест повторной отправки события после временной недоступности Message Broker;
- тест дедупликации: повторная доставка одного `eventId` не создаёт запись в истории дважды;
- тест SMTP Gateway на приём письма и отображение его в правильном ящике;
- тест маршрутизации разных `userId` по логическим шардам через consistent hashing;
- тест атомарности обработки события: падение потребителя между обработкой и commit приводит к повторной доставке и однократному учёту события; потеря ack после commit не создаёт дубль;
- тест синхронной репликации: подтверждённая запись присутствует на реплике (`pg_stat_replication`, `replay_lsn` догнал `flush_lsn`);
- демонстрационный тест автоматического failover: после остановки мастера координатор повышает реплику (`pg_ctl promote`), увеличивает `epoch`, публикует новую карту; Mail повторяет операцию на новом мастере, ранее подтверждённое письмо остаётся доступным; шард работает в деградированном режиме;
- тест отказа реплики при живом мастере: остановка резервного узла не блокирует COMMIT — координатор переводит шард в деградированный режим, а после возврата реплики синхронный режим восстанавливается;
- демонстрационный тест контролируемого возврата узла: узел стартует только для чтения, пересоздаётся как реплика, догоняет WAL, синхронная репликация возвращается (`remote_apply`);
- тест атомарного захвата: после захвата задание имеет `status = 'in_progress'` и не выбирается вторым инстансом до истечения lease; heartbeat продлевает аренду; финальный `UPDATE` с чужим `locked_by` не меняет строку;
- демонстрационный тест отказа инстанса Mail: остановка `Mail-1` во время обработки пачки заданий, перенос запросов на `Mail-2`, передача осиротевших заданий по истечении lease, отсутствие дублей и зависших заданий, возврат `Mail-1` в балансировку;
- демонстрационный тест перераспределения: добавление третьего логического шарда, перенос только части ключей; попытка изменения и удаления в окне `MIGRATING` отклоняется и повторяется после переключения; сверка контрольных сумм до переключения; отметка о прочтении сохраняется; повтор операции по ключу операции находит прежний результат;
- демонстрационный тест восстановления после сбоя брокера на работающем локальном брокере или учебной очереди: накопившиеся события доставляются после восстановления, а история доставки сходится без дублей;
- ручная проверка полного пользовательского сценария: отправка, получение, чтение (письмо помечается прочитанным), безвозвратное удаление и просмотр истории доставки.

**Definition of Done (DoD):**

*Развёртывание и базовая работа:*

- локально запускаются все необходимые сервисы не более чем на четырёх доступных устройствах по схеме размещения из плана разработки;
- пользователь отправляет письмо, видит его в «Отправленных», а получатель видит его во «Входящих» и открывает содержимое: отображаются заголовки и тело, письмо помечается прочитанным, а в списке папки показан признак прочтения;
- при удалении письмо безвозвратно убирается из папки и больше не отображается в интерфейсе; повторная команда удаления возвращает прежний результат без ошибки;
- пользователь открывает историю доставки и видит по каждому отправленному письму статусы «принято в доставку» и «доставлено получателю» со временем событий, а также признак «зафиксировано в истории доставки» (событие учтено Analytics); никакой классификации содержимого письма не выполняется.

*Идемпотентность и дедупликация:*

- повтор отправки с тем же ключом операции не создаёт дубликат и возвращает прежний результат; новая отправка с новым ключом создаёт отдельное письмо;
- повторный приём одного SMTP-сообщения не создаёт второе письмо;
- событие, повторно доставленное в Analytics, не создаёт дубль в истории доставки; отметка об обработке и результат фиксируются одной транзакцией, ack отправляется после commit;
- после восстановления брокера сохранённые события обрабатываются, а история доставки сходится к ожидаемым значениям;
- падение потребителя между обработкой и commit приводит к повторной доставке и однократному учёту события, а потеря ack после commit не создаёт дубль.

*Распределение данных и нагрузки:*

- запросы пользователей маршрутизируются по consistent hashing между двумя логическими шардами, а шард и его реплика находятся на разных узлах хранения;
- при добавлении третьего логического шарда переносятся только диапазоны ключей, попавшие к новым виртуальным узлам; ни одно подтверждённое письмо не теряется и не дублируется после переноса;
- во время переноса диапазона изменяющие операции отклоняются с кодом `MIGRATING` и успешно повторяются после переключения маршрута, поэтому удалённое письмо не «воскресает», а отметка о прочтении не теряется;
- сверка количества и контрольных сумм по диапазону совпала до переключения маршрута; повтор ранее принятой операции после смены владельца находит сохранённый результат, задания доставки и outbox-события диапазона не теряются.

*Частичные отказы:*

- в обычном режиме подтверждённая запись существует на двух узлах (синхронная репликация, `synchronous_commit = remote_apply`); в деградированном режиме — на одном, и признак деградации виден в интерфейсе;
- после отказа мастера координатор автоматически повышает реплику, увеличивает `epoch` и публикует новую карту; Mail повторяет операцию на новом мастере, ранее подтверждённое письмо сохраняется;
- после промоушена шард работает в деградированном режиме: записи принимаются, признак деградации виден в интерфейсе и логах;
- при отказе реплики при живом мастере записи не зависают: координатор переводит шард в деградированный режим, а после возврата реплики и догона WAL синхронная репликация восстанавливается;
- вернувшийся узел принимается только как реплика, догоняет WAL, и синхронная репликация восстанавливается;
- при остановке одного инстанса Mail клиентские операции продолжают выполняться вторым инстансом, дубли не создаются, а восстановленный инстанс возвращается в балансировку;
- задания доставки, которые выполнял отказавший инстанс, не зависают: после истечения lease (≤10 с) их забирает живой инстанс, все письма доставляются ровно один раз, заданий в статусе `in_progress` не остаётся;
- README содержит команды запуска, схему размещения сервисов на устройствах и сценарий итоговой демонстрации, включая показ отказов.
