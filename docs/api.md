## 1. Общие правила

| Правило | Значение |
|---|---|
| Базовый URL | `http://<host>:8080/v1` |
| Формат | `application/json; charset=utf-8` |
| Авторизация (стенд) | заголовок `X-User-Id: <число>` — какой пользователь действует. Настоящей аутентификации в объёме проекта нет, это зафиксировано в ограничениях ТР |
| Идемпотентность | заголовок `Idempotency-Key: <строка>` — обязателен для `POST /messages` |
| Время | ISO 8601 с зоной: `2026-11-15T10:20:30Z` |
| Идентификаторы | `message_id` — строка (заголовок письма), `id` — число (локальный ключ строки в БД) |
| Пагинация | `?limit=50&before=<received_at>` (курсорная, без offset) |

### Формат ошибки (единый для всех эндпоинтов)

```json
{
  "error": {
    "code": "MIGRATING",
    "message": "Раздел обновляется, повторите через несколько секунд",
    "retry_after_ms": 2000
  }
}
```

### Коды ошибок — общий словарь

| `code` | HTTP | Что значит | Что делать клиенту | Что делает сервер |
|---|---|---|---|---|
| `MIGRATING` | 503 | Диапазон пользователя переносится на другой шард (`migrating` в карте координатора) | повторить через `retry_after_ms` (2 000 мс), до 30 с | отклоняет **изменяющие** операции, чтение продолжает работать |
| `UNAVAILABLE` | 503 | Недоступен шард (оба узла хранения) или сервис Mail | повторить через `retry_after_ms` (5 000 мс), показать пользователю «временно недоступно» | возвращает ошибку сразу, не держит запрос |
| `NOT_FOUND` | 404 | Письма нет (в том числе уже удалено) | показать «письмо не найдено», не повторять | — |
| `VALIDATION` | 400 | Некорректный запрос (нет получателя, пустая тема допустима, тело > 1 МБ) | показать текст ошибки, не повторять | — |
| `UNAUTHORIZED` | 401 | Нет или неизвестен `X-User-Id` | показать форму входа | — |
| `INTERNAL` | 500 | Непредвиденная ошибка | повторить один раз, затем показать ошибку | логирует с `trace_id` |

> **Про `CONFLICT`:** это не ошибка. Повтор запроса с тем же `Idempotency-Key` возвращает **HTTP 200** и результат первой операции. См. §3.

Каждый ответ сервера содержит заголовок `X-Trace-Id` — по нему ищутся логи.

## 2. Эндпоинты

### 2.1 `POST /v1/messages` — отправить письмо

Заголовки: `X-User-Id`, `Idempotency-Key` (обязателен), `Content-Type: application/json`.

```json
{
  "to": "bob@mail.example",
  "subject": "Привет",
  "body": "Текст письма"
}
```

Ответ **202 Accepted** (письмо принято в доставку, а не доставлено):

```json
{
  "message_id": "<20261115102030.1.mail.example>",
  "status": "accepted",
  "operation_key": "d7f3-...",
  "accepted_at": "2026-11-15T10:20:30Z"
}
```

Ответ **200 OK** при повторе с тем же `Idempotency-Key` — то же тело, что в первый раз. Новое письмо не создаётся.

| Код | Когда |
|---|---|
| 202 | новая операция принята |
| 200 | повтор той же операции, вернули сохранённый результат |
| 400 `VALIDATION` | нет `to`, адрес не из домена `mail.example`, пустое тело, превышен размер |
| 401 `UNAUTHORIZED` | нет `X-User-Id` или такого пользователя нет |
| 503 `MIGRATING` / `UNAVAILABLE` | см. словарь |

Замечание для B: `operation_key` в теле — это тот же `Idempotency-Key`, продублированный для наглядности. В БД он пишется в `operation_key(user_id, key)`.

### 2.2 `GET /v1/folders/{folder}` — список писем в папке

`folder` ∈ `inbox` | `sent`. Параметры: `limit` (по умолчанию 50, максимум 200), `before` (курсор).

```json
{
  "folder": "inbox",
  "count": 12,
  "messages": [
    {
      "id": 1042,
      "message_id": "<...>",
      "from": "alice@mail.example",
      "to": "bob@mail.example",
      "subject": "Привет",
      "is_read": false,
      "received_at": "2026-11-15T10:20:30Z"
    }
  ],
  "next_before": "2026-11-14T18:02:11Z"
}
```

Тело письма в списке **не отдаётся** — только метаданные. `next_before = null`, если писем больше нет.

### 2.3 `GET /v1/messages/{id}` — открыть письмо

Побочный эффект: письмо помечается прочитанным (`is_read = true`). Это **изменяющая** операция — при `MIGRATING` вернёт 503.

```json
{
  "id": 1042,
  "message_id": "<...>",
  "from": "alice@mail.example",
  "to": "bob@mail.example",
  "subject": "Привет",
  "body": "Текст письма",
  "is_read": true,
  "received_at": "2026-11-15T10:20:30Z"
}
```

Письмо другого пользователя → **404 `NOT_FOUND`** (не 403: не подтверждаем существование чужих писем).

### 2.4 `DELETE /v1/messages/{id}` — удалить письмо

Удаление **безвозвратное** (правило зафиксировано в ТР). Тело ответа:

```json
{"id": 1042, "status": "deleted", "deleted_at": "2026-11-15T12:00:00Z"}
```

**Идемпотентно:** повторный `DELETE` того же письма возвращает **200** с тем же телом, а не 404. Это прямо требуется в DoD («повторная команда удаления возвращает прежний результат без ошибки») — значит сервер должен помнить факт удаления (`deleted_at` в `message`), а не просто выкидывать строку.

> Вот почему в `schema.sql` есть поле `deleted_at` при «безвозвратном» удалении: строка помечается и не отдаётся в интерфейс, но факт удаления сохраняется, чтобы повтор возвращал прежний результат.

### 2.5 `GET /v1/delivery-history` — история доставки

```json
{
  "items": [
    {
      "message_id": "<...>",
      "subject": "Привет",
      "to": "bob@mail.example",
      "statuses": [
        {"code": "accepted",  "label": "принято в доставку",   "at": "2026-11-15T10:20:30Z"},
        {"code": "delivered", "label": "доставлено получателю","at": "2026-11-15T10:20:31Z"}
      ],
      "recorded_in_history": true
    }
  ],
  "updating": false
}
```

- `statuses` строится из событий Analytics: `message.accepted` → `accepted`, `message.delivered` → `delivered`.
- `recorded_in_history` — признак «событие учтено Analytics» (в ТР он назван «зафиксировано в истории доставки»).
- `updating: true` — брокер отстаёт или недоступен; интерфейс показывает «данные обновляются». Клиент при этом **не** считает это ошибкой.

Сортировка — по `accepted.at` по убыванию. Письма, у которых нет ни одного события, в выдачу не попадают, но их наличие в «Отправленных» от этого не страдает.

### 2.6 Служебные

| Эндпоинт | Назначение | Кому нужен |
|---|---|---|
| `GET /health` | `{"status":"ok"}` — используется для переключения инстансов Mail | C (балансировка), D (проверки) |
| `GET /v1/stand/status` | карта маршрутов от координатора: шарды, `epoch`, `degraded`, `migrating` | A (отладка), D (демо) |

`GET /v1/stand/status` — только для стенда, в интерфейс пользователя не выводится (кроме индикатора деградации).

```json
{
  "shards": [
    {"name": "shard1", "master": "127.0.0.1:5433", "replica": "127.0.0.1:5434",
     "epoch": 1, "degraded": false, "migrating": null}
  ]
}
```

## 3. Идемпотентность — правила, которые нельзя нарушать

1. `Idempotency-Key` обязателен для `POST /messages`. Нет заголовка → **400 `VALIDATION`**.
2. Ключ уникален **в пределах пользователя**: `primary key (user_id, key)`.
3. Одна и та же операция = тот же ключ. Две намеренные отправки с одинаковыми темой и текстом — **два разных ключа** и два письма.
4. Сервер сохраняет `operation_key.result` (JSON ответа) в той же транзакции, что и письмо/задание доставки.
5. Повтор возвращает сохранённый `result` — даже если с момента первой операции прошло время.
6. Клиент генерирует новый ключ (UUID v4) на каждую новую отправку и **переиспользует** его при ретрае.

Псевдокод на стороне Mail (для B):

```
begin;
  if exists (select 1 from operation_key where user_id=:u and key=:k) then
      return saved_result;          -- 200, новая транзакция не нужна
  end if;
  insert letter into sent;
  insert delivery_job;
  insert outbox('accepted:'||message_id);
  insert operation_key(user_id, key, result);
commit;
```

## 4. Внутренний контракт: SMTP Gateway → Mail

Не часть публичного API, но граница между B и остальными.

```
POST /internal/v1/inbound
Content-Type: application/json
{ "from": "...", "to": "...", "subject": "...", "body": "...",
  "message_id": "<...>", "raw_size": 1234 }
```

| Ответ | Смысл для SMTP Gateway |
|---|---|
| 200 | письмо сохранено → отвечать заглушке/клиенту `250 OK` |
| 409 | дубликат по `Message-ID` в ящике → тоже `250 OK` (повтор не ошибка) |
| 503 `UNAVAILABLE` | не смогли сохранить → `451 Try again later`, **не** `250` |

Правило из ТР: `250 OK` отдаётся только после того, как Mail сохранил письмо. Иначе письмо будет потеряно при отказе.

## 5. Границы между разработчиками (короткая шпаргалка)

| Что | Кто владеет | Кто читает |
|---|---|---|
| `schema.sql`, функции аренды | **A** | B, C |
| Таблицы, поля, индексы | **A** (структура) | B (смысл полей — по этому файлу) |
| Эндпоинты `/v1/*`, коды ошибок, формат JSON | **C** | B реализует внутри |
| Логика записи в `message`/`outbox`, worker доставки | **B** | A (ревью SQL) |
| Брокер, Analytics, `delivery-history` | **C** | B (публикует события) |
| Карта маршрутов, `epoch`, `degraded`, `migrating` | **A** | C (отдаёт в `/stand/status`), B (`MIGRATING` в ответах) |

**Правило изменения контракта:** сначала PR в этот файл, потом код. Если B нужен новый эндпоинт — его добавляет C, а не B в обход (иначе в `main` окажутся два несовместимых API).

## 6. Примеры для проверки руками (Windows PowerShell)

`curl` в Windows — это алиас `Invoke-WebRequest`; используйте `curl.exe`, чтобы получить настоящий curl:

```powershell
# отправить письмо
curl.exe -X POST http://localhost:8080/v1/messages `
  -H "Content-Type: application/json" `
  -H "X-User-Id: 1" `
  -H "Idempotency-Key: 11111111-1111-1111-1111-111111111111" `
  -d '{\"to\":\"bob@mail.example\",\"subject\":\"Привет\",\"body\":\"Тест\"}'

# повторить ровно то же — должен прийти 200 и тот же message_id, второго письма быть не должно
curl.exe -X POST http://localhost:8080/v1/messages `
  -H "Content-Type: application/json" -H "X-User-Id: 1" `
  -H "Idempotency-Key: 11111111-1111-1111-1111-111111111111" `
  -d '{\"to\":\"bob@mail.example\",\"subject\":\"Привет\",\"body\":\"Тест\"}'

# список входящих
curl.exe -H "X-User-Id: 1" "http://localhost:8080/v1/folders/inbox?limit=10"

# история доставки
curl.exe -H "X-User-Id: 1" http://localhost:8080/v1/delivery-history
```

Эти три команды — фактически первые приёмочные проверки DoD (отправка, идемпотентность, чтение списка). D может начать с них, ещё до появления интерфейса.
